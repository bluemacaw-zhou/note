## 一、环境准备

### npm 和 pnpm 的关系

npm 是 Node.js 自带的包管理器，装完 Node.js 就有了。pnpm 是第三方的更快包管理器，用硬链接/符号链接共享模块文件，磁盘占用更小、安装速度更快。两者功能上基本等价，常见命令都能对应（`install`、`add`、`run` 等）。

关系是：**用 npm 安装 pnpm，之后项目操作全用 pnpm**。这个项目在 `package.json` 的 `packageManager` 字段锁定了 pnpm 版本，用 npm 直接安装依赖会报警告。

### 依赖版本要求

| 工具 | 要求 | 说明 |
|------|------|------|
| Node.js | ≥ 22.16.0 | 项目 `package.json` engines 字段声明 |
| pnpm | 10.23.0 | `packageManager` 字段锁定版本 |
| bun | 任意 | 部分构建步骤使用 |
| git | 任意 | 版本管理 |

### 安装命令

```bash
# 用 npm 安装 pnpm（只此一次，之后用 pnpm）
npm install -g pnpm@10.23.0

# bun（安装脚本自动写入 ~/.zshrc）
curl -fsSL https://bun.sh/install | bash
```

## 二、从源码构建

```bash
git clone https://github.com/bluemacaw-zhou/openclaw.git ~/workspace/openclaw
cd ~/workspace/openclaw

# 安装依赖（1321 个包，约 2 分钟）
pnpm install

# 构建（生成 dist/ 产物）
pnpm build
```

构建产物在 `dist/`，入口为 `dist/entry.js`。

### 正确的构建步骤

```bash
cd ~/workspace/openclaw
pnpm install --force   # ⚠️ 必须加 --force，否则部分包不会正确链接
pnpm build
node dist/entry.js --version   # 验证：输出版本号即成功
```

**为什么 `pnpm install --force` 是必须的：**

pnpm 用内容寻址全局 store + 硬链接的方式管理依赖。正常 `pnpm install` 看到 `node_modules/.pnpm/` 下已有目录就认为"已安装"，不会重新链接。但某些包（实测为 `undici@7.24.4`）的虚拟 store 目录会出现"只有部分文件"的状态（仅 `docs/`、`lib/`，缺少 `index.js`、`package.json`），全局 store 里文件是完整的，只是链接没有正确建立。`--force` 强制重新从全局 store 链接所有文件，修复这个问题。

不加 `--force` 的后果：构建看似成功，但运行时报：
```
Error: Cannot find package 'xxx/node_modules/undici/index.js'
```

### 构建输出中的非致命报错

`pnpm build` 内部是多个步骤用 `&&` 串联，实践中会看到各种警告。判断标准只有一个：**`node dist/entry.js --version` 能输出版本号**。

| 报错 / 警告 | 原因 | 处理 |
|------------|------|------|
| `Ignored build scripts: @discordjs/opus, @tloncorp/tlon-skill` | pnpm `onlyBuiltDependencies` 白名单，不在列表的包的 install scripts 被跳过 | 忽略，不影响核心功能 |
| `[UNRESOLVED_IMPORT] openai / @opentelemetry/api` | 可选扩展（LanceDB、OpenTelemetry）的依赖未安装，打包器标注为外部依赖 | 忽略，这些扩展不使用 |
| TypeScript `TS2307 Cannot find module ...` 类型错误 | `build:plugin-sdk:dts` 步骤末尾是 `|| true`，不会中止构建 | 忽略 |
| `A2UI bundle up to date; skipping.` | canvas 预构建产物存在，跳过重新打包 | 正常 |

## 三、如何发现 Provider 和模型配置（探索过程）

拿到一个新的 OpenClaw 环境，先看 help 了解有哪些命令：

```bash
node dist/entry.js --help
```

输出的子命令列表里有 `onboard`，描述是 "initial setup wizard"。这就是配置模型和 channel 的入口。

拿到一个新的 OpenClaw 环境，什么文档都没有的情况下，按以下顺序探索：

### 第一步：看 `onboard --help`

这是最直接的信息源，所有支持的 provider 都列在 `--auth-choice` 参数的枚举值里：

```bash
node dist/entry.js onboard --help
```

输出中找到 `--auth-choice` 一行，所有支持的 provider 都在里面，例如：

```
--auth-choice ... zai-api-key|zai-coding-global|zai-coding-cn|zai-global|zai-cn ...
```

命名规律：
- `zai-*` 开头 → 智谱 Z.AI 系列
- `cn` 结尾 → 国内端点
- `coding` → Coding Plan（有专属优惠定价）
- 其他类推：`gemini-api-key`、`moonshot-api-key`、`ollama` 等

光看这个枚举就能推断出选哪个，不需要查外部文档。

### 第二步：配置后用 `models` 命令查可用模型

```bash
node dist/entry.js models
```

Gateway 启动后，此命令会从 provider 拉取模型列表，直接显示可用的模型 ID。不需要事先知道模型名称。

### 第三步（按需）：看源码

如果 help 信息不够，直接搜源码：

```bash
grep -r "zai" ~/workspace/openclaw/src --include="*.ts" -l
```

### 第四步（按需）：查 provider 官方文档

部分 provider 有专门的 OpenClaw 集成章节，例如智谱：`docs.bigmodel.cn/cn/guide/develop/openclaw`。

> **探索优先级：`--help` → `models` 命令 → 源码 → 官方文档**
> 大多数情况下前两步就够了。这个顺序适用于 OpenClaw 所有配置项的探索。

## 四、配置智谱 GLM

### 环境变量

在 `~/.zshrc` 中添加：

```bash
export ZHIPUAI_API_KEY=<your_api_key>
```

> ⚠️ 注意：API Key 末尾不能有多余字符（如 `)`），否则返回「令牌已过期或验证不正确」。

验证 key 是否有效：

```bash
curl -s -X POST "https://open.bigmodel.cn/api/paas/v4/chat/completions" \
  -H "Authorization: Bearer $ZHIPUAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"glm-4-flash","messages":[{"role":"user","content":"回复 API正常 四个字"}],"max_tokens":20}'
```

### 非交互式 onboard 配置

```bash
cd ~/workspace/openclaw

node dist/entry.js onboard \
  --non-interactive \
  --accept-risk \
  --auth-choice zai-coding-cn \
  --zai-api-key "$ZHIPUAI_API_KEY" \
  --skip-channels \
  --skip-skills \
  --skip-daemon \
  --skip-search \
  --skip-ui \
  --skip-health
```

配置写入 `~/.openclaw/openclaw.json`，模型默认为 `zai/glm-5`。

**`--auth-choice` 可选值（智谱相关）：**

| 值 | 说明 |
|----|------|
| `zai-coding-cn` | 智谱 Coding Plan 国内端点（推荐） |
| `zai-cn` | 智谱标准国内端点 |
| `zai-api-key` | 通用 API Key 方式 |

## 五、openclaw 命令与 gateway 的关系

### `openclaw` 命令是什么

从源码构建后没有全局 `openclaw` 二进制。有三种等效的运行方式：

| 命令 | 说明 |
|------|------|
| `node dist/entry.js <subcommand>` | 直接运行构建产物，最明确 |
| `node openclaw.mjs <subcommand>` | 包装器：先做 Node 版本检查，再加载 `dist/entry.js` |
| `pnpm openclaw <subcommand>` | 调用 `scripts/run-node.mjs`，开发时用，会检查是否需要重建 |

日常使用推荐 `node openclaw.mjs`，或配一个 alias：

```bash
alias openclaw='node ~/workspace/openclaw/openclaw.mjs'
```

### gateway 是什么，和"本体"什么关系

**Gateway 就是 openclaw 的运行时本体**，是长期驻留的后台服务进程，负责：
- 连接各 channel（Slack、Telegram 等），监听外部消息
- 将消息路由给 agent，执行 skill
- 暴露本地 RPC 端口 `127.0.0.1:18789`

**CLI 命令**（`models`、`status`、`sessions`、`agent --message` 等）都是通过 RPC 端口与 gateway 通信的客户端。Gateway 不启动，这些命令会报 "connection refused"。

```
用户消息（Slack/Telegram/…）
        ↓
    [Gateway 进程]  ← 长期驻留
        ├── channel adapters
        ├── agent runtime
        └── RPC :18789
              ↑
    node dist/entry.js models   ← 短暂的 CLI 客户端进程
    node dist/entry.js sessions
    node dist/entry.js agent --message "xxx"
```

**启动 gateway ≠ 另外单独启动 openclaw 主程序**，gateway 进程本身就包含完整的 agent 运行时，不需要额外启动其他进程。

### 启动 Gateway

#### 开发模式（watch，源码改动自动重建）

```bash
cd ~/workspace/openclaw
pnpm gateway:watch
```

### 直接启动（前台，不监听源码变化）

```bash
node dist/entry.js gateway run
```

### 开机自启动（launchd 服务，推荐生产使用）

OpenClaw 内置 launchd 支持，一条命令安装并注册为 LaunchAgent：

```bash
# 安装为系统服务（开机自启）
node dist/entry.js gateway install

# 启动
node dist/entry.js gateway start

# 停止
node dist/entry.js gateway stop

# 重启
node dist/entry.js gateway restart

# 卸载服务
node dist/entry.js gateway uninstall
```

安装后生成：
- LaunchAgent plist：`~/Library/LaunchAgents/ai.openclaw.gateway.plist`
- 日志文件：`~/.openclaw/logs/gateway.log`

### 查看服务状态

```bash
node dist/entry.js gateway status
```

输出示例：
```
Runtime: running (pid 63331, state active)
RPC probe: ok
Listening: 127.0.0.1:18789
```

### 查看日志

```bash
# 实时滚动日志（主日志，按日期）
tail -f /tmp/openclaw/openclaw-$(date +%Y-%m-%d).log

# 服务日志（launchd 管理时）
tail -f ~/.openclaw/logs/gateway.log

# 查看 channel 最近日志
node dist/entry.js channels logs

# 查看 gateway 状态 + 健康检查
node dist/entry.js status
```

Web Control UI 地址：`http://127.0.0.1:18789`

## 六、CLI Chat 测试命令

### 基本对话

```bash
# 指定 main agent 发送消息
node dist/entry.js agent --agent main --message "你好"

# 指定 session ID
node dist/entry.js agent --session-id <id> --message "消息内容"

# 指定收件人（E.164 格式电话号码）
node dist/entry.js agent --to +8613800138000 --message "消息内容"
```

> **注意**：`--local` 和单独 `--message` 不够，必须至少指定 `--agent`、`--session-id`、`--to` 之一。

### 其他常用命令

```bash
# 查看帮助
node dist/entry.js --help
node dist/entry.js agent --help

# 查看已连接 channel 状态
node dist/entry.js status

# 查看可用模型
node dist/entry.js models

# 查看 session 列表
node dist/entry.js sessions

# 安全审计
node dist/entry.js security audit --deep
```

## 七、QQ Channel（已放弃）

QQ 开放平台接入 openclaw-qqbot 插件在技术上是可行的（channel 可以 connect），但实际使用时 **QQ 平台会对机器人发出的消息进行内容审核和拦截**，普通文字消息也可能被屏蔽，无法作为可靠的通信通道。

**结论：不使用 QQ 作为 openclaw 的通信渠道，改用 Slack。**

### 附：插件配置探索记录（供参考）

`channels add --channel qqbot` 命令无效，因为 `--channel` 是硬编码内置列表，第三方插件不在其中。实际配置方式是直接写 `~/.openclaw/openclaw.json`，字段见插件的 `onboarding.ts` 源码。这个探索过程揭示了一个通用规律：**第三方插件不走 `channels add`，要看插件源码找配置路径**。
