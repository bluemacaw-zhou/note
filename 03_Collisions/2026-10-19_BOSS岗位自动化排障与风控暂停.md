随后要求手动调试发现岗位与获取 securityId，并询问定时任务是否指向 `workspace/job` 下脚本；该路径对应关系尚未确认。

### 发现岗位：入口状态与证据要求

- 用户查阅错误日志后提出：历史页面停在聊天页，导致任务入口变化；应先点击底部“职位”，统一入口。这是用户提出的诊断，不能据此解释所有失败。
- 对“已识别职位列表，随后切换推荐超时”的说法，用户追问具体日志文件依据，并明确要求将 `discover.log` 与 `failures` 下具体 JSON 关联分析，不能只看汇总日志。
- 用户手动观察到“推荐、附近、最新”页签 UI 在点击时瞬时切换，岗位数据可能稍后加载；因此质疑把 UI 未切换归因于网络等待。
- 用户追问 `AXPress` 返回成功但实际点击失败的依据；来源中没有官方说明或确定结论。
- 调试中追问切换与采集间的等待、超时依据以及“总共等待 8 秒”的解释；该数值只是对话中的追问，未核实为实际代码配置。

### 发现岗位：明确要求的处理逻辑

1. 检查 App 是否启动，再检查窗口是否最小化并还原，最后点击“职位”。
2. 对页签切换失败，要求截图并重试三次；三次均使用相同接口，不采用首次接口、后续坐标的混合策略。用户追求稳定、简单、便于排查。
3. 页签切换后仍等待若干秒稳定，再采集岗位信息；用户认为短时间重复切换不会改变岗位信息，这是设计依据，未独立验证。
4. 失败截图与 JSON 统一命名，能够直接识别为一对。
5. 岗位详情点击与页签切换分开处理：点击岗位后短暂等待，立即读取；若页面不符合预期，不启动定时轮询，不重试该岗位，记录 JSON 与截图后跳过。用户接受当天漏掉的岗位未来可能再次被发现。
6. 正常成功出口仅按实际入库岗位数量达到目标判断；不希望以尝试次数上限作为成功条件。异常出口为到达截止时间，或界面状态异常导致代码无法继续执行。

用户曾清理 10 月 19 日日志并要求重跑，随后又清空日志、指定当次截止时间为北京时间 11:45。用户追问“一次失败为什么产生 17 个 JSON”，来源没有最终解释，仍需核对失败记录粒度。
