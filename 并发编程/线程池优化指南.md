## 📋 文档概述

**目标**: 在4核CPU容器环境下，优化消息处理系统的线程池配置，达到100条消息/秒的吞吐量目标

**背景**:
- 当前环境：2核CPU × 2实例，峰值20条/秒出现消息积压
- 优化目标：升级到4核CPU后，单实例达到40-50条/秒，3台实例总计100条/秒
- 核心挑战：线程池配置不合理导致CPU利用率低、消息积压

**适用版本**: Spring Boot 3.4.1 + Java 17

---

## 1️⃣ 代码分析

### 1.1 当前线程池配置

**文件位置**: `src/main/java/cn/com/wind/server/config/OrchestratorThreadPoolConfig.java`

```java
@Configuration
public class OrchestratorThreadPoolConfig {

    private static final int CORE_POOL_SIZE = 10;          // 核心线程数
    private static final int MAXIMUM_POOL_SIZE = 30;       // 最大线程数
    private static final long KEEP_ALIVE_TIME = 60L;       // 空闲保活时间
    private static final int QUEUE_CAPACITY = 1000;        // 队列容量

    @Bean("messageTaskOrchestratorExecutor")
    public ThreadPoolExecutor messageTaskOrchestratorExecutor() {
        ThreadPoolExecutor executor = new MDCThreadPoolTaskExecutor(
                CORE_POOL_SIZE,
                MAXIMUM_POOL_SIZE,
                KEEP_ALIVE_TIME,
                TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(QUEUE_CAPACITY),
                new WmThreadFactory("MessageTask-Pool"),
                new RetryRejectedExecutionHandler()
        );

        // 监控配置
        ThreadPoolMonitor monitor = new ThreadPoolMonitor(executor, "MessageTask");
        monitor.setQueueSizeAlertThreshold(80);
        monitor.setActiveThreadAlertThreshold(90);
        monitor.setBlockTimeAlertMs(1000);
        monitor.startMonitoring(300);

        return executor;
    }
}
```

**问题诊断**:
- ❌ 10个核心线程在2核CPU上运行，线程竞争比 = 10:2 = 5:1（严重过载）
- ❌ 所有任务（CPU密集型 + IO密集型）共用一个线程池，资源分配不合理
- ❌ 最大30个线程对于高IO等待的任务来说可能不够

### 1.2 任务流程分析

**消息处理流程**: `MsgConsumer.onMessage()` → `MessageTaskOrchestrator.executeAsync()` → 任务链执行

#### 任务编排结构

```java
MessageProcessingChain (主任务链)
├─ MsgProcessChain (消息处理)
│   ├─ ValidationAndIdGeneration (并行组)
│   │   ├─ ValidationTask              // CPU密集型，~5-10ms
│   │   └─ MessageIdGenerationTask     // CPU密集型，~1-2ms
│   └─ MessageTypeRouting (条件分支)
│       ├─ PrivateMsgProcessTask       // IO密集型，~50-100ms (MySQL)
│       └─ GroupMsgProcessTask         // IO密集型，~50-100ms (MySQL)
└─ MonitorAndRecallGroup (并行组)
    ├─ MonitorStorageGroup (并行组)
    │   ├─ MonitorRecordSaveTask            // IO密集型，~80-120ms (MySQL)
    │   ├─ ElasticsearchStorageTask         // IO密集型，~100-200ms (ES)
    │   └─ HistoryChatUserStorageTask       // IO密集型，~80-120ms (MySQL)
    └─ RecallMessageChain (条件执行，1%消息)
```

#### 并行度分析

```java
// 关键代码片段：MonitorStorageOrchestrator
@Component
public class MonitorStorageOrchestrator {

    @Autowired
    @Qualifier("messageTaskOrchestratorExecutor")
    private ExecutorService executorService;  // ← 所有任务共用此线程池

    public TaskGroup createTaskGroup() {

                .addTask(monitorRecordSaveTask)
                .addTask(elasticsearchStorageTask)
                .addTask(historyChatUserStorageTask);
    }

```

**并行任务线程需求**:
```
单条消息的最大并行度 = 3个任务（MonitorStorageGroup）

如果同时处理10条消息：
MonitorStorageGroup阶段需要：10 × 3 = 30个线程

但核心线程只有10个：
- 10个任务立即执行
- 20个任务进入队列等待
- 结果：消息处理延迟增加，吞吐量下降
```

### 1.3 性能瓶颈定位

#### 瓶颈1: 线程数与CPU核数不匹配

```
2核CPU运行10个核心线程：
├─ 线程竞争比：10:2 = 5:1
├─ 上下文切换频繁：CPU时间浪费在调度上
├─ 实际每线程可用CPU：0.2核
└─ 结果：吞吐量严重下降

4核CPU运行10个核心线程：
├─ 线程竞争比：10:4 = 2.5:1
├─ 仍存在竞争，但比2核改善
└─ 但对于IO密集型任务，10个线程仍然不够
```

#### 瓶颈2: CPU密集型任务被IO任务阻塞

```
时间线分析：
T0: 10个线程都在执行IO任务（等待MySQL/ES响应）
T1: ValidationTask到达 → 需要排队等待
T2: 等待100ms后才获得线程 → 延迟增加
T3: ValidationTask执行5ms后完成

问题：轻量级CPU任务（5ms）需要等待100ms才能执行
```

#### 瓶颈3: 并行任务组线程不足

```
理论需求：
├─ 峰值20条/秒消息
├─ 每条消息MonitorStorageGroup需要3个线程
└─ 同时处理的消息数：假设10条（0.5秒窗口）

线程需求：10 × 3 = 30个线程

实际情况：
├─ 核心线程：10个
├─ 需要额外创建：20个线程（达到最大30）
└─ 线程创建开销 + 队列等待 → 性能下降
```

## 2️⃣ 理论计算

### 2.1 任务类型分类

#### CPU密集型任务

| 任务名称 | 主要操作 | 平均耗时 | IO等待 |
|---------|---------|---------|-------|
| ValidationTask | 参数校验、逻辑判断 | 5-10ms | 无 |
| MessageIdGenerationTask | 雪花算法生成ID | 1-2ms | 无 |

**特征**:
- 纯CPU计算，无IO等待
- 执行快速（毫秒级）
- 对线程数敏感（线程多反而慢）

#### IO密集型任务

| 任务名称 | 主要操作 | 平均耗时 | IO占比 |
|---------|---------|---------|--------|
| PrivateMsgProcessTask | MySQL写入 | 50-100ms | 80% |
| GroupMsgProcessTask | MySQL写入 | 50-100ms | 80% |
| MonitorRecordSaveTask | MySQL写入 | 80-120ms | 85% |
| ElasticsearchStorageTask | ES写入 | 100-200ms | 90% |
| HistoryChatUserStorageTask | MySQL写入 | 80-120ms | 85% |

**特征**:
- 大部分时间等待网络/磁盘IO
- 执行较慢（数十到数百毫秒）
- 需要大量线程充分利用IO等待时间

### 2.2 线程数计算公式

#### 公式1: CPU密集型线程数

```
线程数 = CPU核数 + 1

对于4核CPU:
线程数 = 4 + 1 = 5个

原理：
- CPU密集型任务，线程数超过CPU核数会导致频繁上下文切换
- +1是为了应对偶尔的页面错误或其他中断
```

#### 公式2: IO密集型线程数

```
线程数 = CPU核数 × (1 + IO等待时间/CPU计算时间)

假设IO密集型任务的时间分布：
- CPU计算时间：20ms
- IO等待时间：80ms
- 比例：80:20 = 4:1

对于4核CPU:
线程数 = 4 × (1 + 80/20) = 4 × (1 + 4) = 4 × 5 = 20个

不同IO比例的线程数：
├─ IO:CPU = 3:1 → 4 × (1+3) = 16个
├─ IO:CPU = 4:1 → 4 × (1+4) = 20个
└─ IO:CPU = 5:1 → 4 × (1+5) = 24个
```

#### 公式3: Little's Law（利特尔法则）

```
所需并发数 = 吞吐量(TPS) × 平均响应时间(秒)

场景1：目标40条/秒，平均响应时间150ms
所需并发数 = 40 × 0.15 = 6个线程

场景2：目标50条/秒，平均响应时间200ms
所需并发数 = 50 × 0.2 = 10个线程

注意：此公式给出的是理想并发数，实际配置需要考虑：
- 任务的并行度（如MonitorStorageGroup的3个并行任务）
- 队列缓冲能力
- 峰值流量的突发性
```

### 2.3 4核CPU的线程配置计算

#### 场景分析：100条/秒目标拆解

```
目标吞吐量：100条/秒
实例配置：4核CPU × 3实例
单实例目标：100 / 3 ≈ 35条/秒
峰值考虑：×1.5倍 ≈ 50条/秒

单条消息处理时间估算：
├─ ValidationAndIdGeneration: 10ms（并行）
├─ MessageStorage: 80ms（MySQL写入）
├─ MonitorStorageGroup: 150ms（3个并行任务，取最长）
└─ 总计：~240ms

理论并发数：35 × 0.24 = 8.4 ≈ 9个并发消息
```

#### 考虑并行度的线程需求

```
单条消息的并行任务峰值：3个（MonitorStorageGroup）

如果9条消息同时处理：
├─ ValidationAndIdGeneration阶段：9 × 2 = 18个线程需求
├─ MessageStorage阶段：9 × 1 = 9个线程需求
└─ MonitorStorageGroup阶段：9 × 3 = 27个线程需求

峰值线程需求：27个

考虑队列缓冲和流量突发，建议配置：
├─ 核心线程：12-16个（支持4-5条消息同时处理）
├─ 最大线程：24-32个（支持8-10条消息同时处理）
└─ 队列容量：2000（缓冲20秒峰值流量）
```

#### 不同方案的理论吞吐量

```
方案A：单线程池（12核心/24最大）
├─ 假设12个线程同时工作
├─ 每个线程处理周期：240ms
├─ 单线程吞吐：1000ms / 240ms ≈ 4.2条/秒
├─ 12线程总吞吐：4.2 × 12 ≈ 50条/秒
└─ 考虑并行度损耗：实际吞吐 ≈ 35-40条/秒

方案B：拆分线程池（CPU:4/8 + IO:8/16）
├─ CPU任务快速处理，不阻塞
├─ IO任务充分并发（16个线程）
├─ 理论IO线程吞吐：16 × 4 = 64条/秒
└─ 实际吞吐（考虑协调开销）：45-50条/秒
```

## 3️⃣ 方案选择

### 方案A: 单线程池优化（推荐快速实施）

#### 配置代码

```java
package cn.com.wind.server.config;

import cn.com.wind.IMStarter.thread.MDCThreadPoolTaskExecutor;
import cn.com.wind.IMStarter.thread.RetryRejectedExecutionHandler;
import cn.com.wind.IMStarter.thread.ThreadPoolMonitor;
import cn.com.wind.IMStarter.thread.WmThreadFactory;
import lombok.extern.slf4j.Slf4j;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import java.util.concurrent.*;

/**
 * 方案A: 单线程池优化配置（4核CPU）
 *
 * 优点：
 * - 配置简单，只需修改一个文件
 * - 风险低，容易回滚
 * - 快速见效
 *
 * 缺点：
 * - CPU任务可能被IO任务阻塞
 * - 性能提升有限（约30-40%）
 *
 * 适用场景：
 * - 快速解决当前问题
 * - 团队资源有限
 * - 暂无充足测试时间
 */
@Slf4j
@Configuration
public class OrchestratorThreadPoolConfig {

    private static final int CPU_CORES = 4;

    // 核心线程数：4核 × 3 = 12
    // 原则：IO密集型任务需要更多线程
    private static final int CORE_POOL_SIZE = CPU_CORES * 3;

    // 最大线程数：4核 × 6 = 24
    // 原则：应对突发流量，但不能过大（避免上下文切换）
    private static final int MAXIMUM_POOL_SIZE = CPU_CORES * 6;

    // 保活时间：60秒
    private static final long KEEP_ALIVE_TIME = 60L;

    // 队列容量：2000
    // 原则：缓冲20秒峰值流量（100条/秒 × 20秒）
    private static final int QUEUE_CAPACITY = 2000;

    /**
     * 消息任务编排器线程池
     */
    @Bean("messageTaskOrchestratorExecutor")
    public ThreadPoolExecutor messageTaskOrchestratorExecutor() {
        ThreadPoolExecutor executor = new MDCThreadPoolTaskExecutor(
                CORE_POOL_SIZE,
                MAXIMUM_POOL_SIZE,
                KEEP_ALIVE_TIME,
                TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(QUEUE_CAPACITY),
                new WmThreadFactory("MessageTask-Pool"),
                new RetryRejectedExecutionHandler()
        );

        log.info("Created MessageTaskOrchestrator thread pool: core={}, max={}, queueCapacity={}, cpuCores={}",
                CORE_POOL_SIZE, MAXIMUM_POOL_SIZE, QUEUE_CAPACITY, CPU_CORES);

        // 添加监控
        ThreadPoolMonitor monitor = new ThreadPoolMonitor(executor, "MessageTask");
        monitor.setQueueSizeAlertThreshold(80);      // 队列使用率80%告警
        monitor.setActiveThreadAlertThreshold(90);   // 活跃线程90%告警
        monitor.setBlockTimeAlertMs(1000);           // 阻塞超过1秒告警
        monitor.startMonitoring(300);                // 每5分钟检查一次

        return executor;
    }
}
```

#### 预期性能

```
单实例（4核CPU）：
├─ 吞吐量：35-40条/秒
├─ 平均延迟：150-200ms
├─ CPU利用率：70-80%
└─ 队列积压：正常情况下 < 100

3实例总计：
├─ 总吞吐量：105-120条/秒
└─ 余量：5-20%（应对突发流量）
```

#### 优缺点分析

**优点**:
- ✅ 实施简单：仅修改一个配置文件
- ✅ 风险低：易于理解和回滚
- ✅ 快速见效：30分钟内完成部署

**缺点**:
- ⚠️ CPU任务可能被IO任务阻塞
- ⚠️ 性能提升有限（相比拆分方案）
- ⚠️ 单点故障时压力大

### 方案B: 拆分线程池（推荐长期方案）

#### 配置代码

```java
package cn.com.wind.server.config;

import cn.com.wind.IMStarter.thread.MDCThreadPoolTaskExecutor;
import cn.com.wind.IMStarter.thread.RetryRejectedExecutionHandler;
import cn.com.wind.IMStarter.thread.ThreadPoolMonitor;
import cn.com.wind.IMStarter.thread.WmThreadFactory;
import lombok.extern.slf4j.Slf4j;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import java.util.concurrent.*;

/**
 * 方案B: 拆分线程池配置（4核CPU）
 *
 * 设计理念：
 * - CPU密集型任务和IO密集型任务使用不同线程池
 * - 各司其职，避免相互干扰
 * - 资源利用最大化
 *
 * 优点：
 * - 性能最优（提升40-50%）
 * - CPU任务零等待
 * - IO任务充分并发
 * - 易于监控和调优
 *
 * 缺点：
 * - 代码修改量大
 * - 需要充分测试
 * - 维护复杂度稍高
 *
 * 适用场景：
 * - 追求极致性能
 * - 有充足测试资源
 * - 长期规划优化
 */
@Slf4j
@Configuration
public class OrchestratorThreadPoolConfig {

    private static final int CPU_CORES = 4;

    // ==================== CPU密集型线程池 ====================

    /**
     * CPU密集型任务线程池
     *
     * 用于：
     * - ValidationTask（参数校验）
     * - MessageIdGenerationTask（ID生成）
     *
     * 特点：
     * - 核心线程 = CPU核数（避免上下文切换）
     * - 最大线程 = CPU核数 × 2（应对突发）
     * - 小队列（快速失败）
     * - AbortPolicy（CPU任务应快速执行）
     */
    @Bean("cpuIntensiveExecutor")
    public ThreadPoolExecutor cpuIntensiveExecutor() {
        ThreadPoolExecutor executor = new MDCThreadPoolTaskExecutor(
                CPU_CORES,              // 核心：4
                CPU_CORES * 2,          // 最大：8
                60L,
                TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(500),
                new WmThreadFactory("CPU-Task-Pool"),
                new ThreadPoolExecutor.AbortPolicy()
        );

        log.info("Created CPU-Intensive thread pool: core={}, max={}, queueCapacity={}",
                CPU_CORES, CPU_CORES * 2, 500);

        ThreadPoolMonitor monitor = new ThreadPoolMonitor(executor, "CPU-Task");
        monitor.setQueueSizeAlertThreshold(80);
        monitor.setActiveThreadAlertThreshold(90);
        monitor.setBlockTimeAlertMs(100);  // CPU任务应该很快，100ms告警
        monitor.startMonitoring(300);

        return executor;
    }

    // ==================== IO密集型线程池 ====================

    /**
     * IO密集型任务线程池
     *
     * 用于：
     * - PrivateMsgProcessTask / GroupMsgProcessTask（消息存储）
     * - MonitorStorageGroup（监控存储组）
     * - RecallMessageChain（撤回消息链）
     *
     * 特点：
     * - 核心线程 = CPU核数 × 2（充分利用IO等待）
     * - 最大线程 = CPU核数 × 4（高并发）
     * - 大队列（缓冲流量）
     * - RetryRejectedExecutionHandler（不能丢消息）
     */
    @Bean("ioIntensiveExecutor")
    public ThreadPoolExecutor ioIntensiveExecutor() {
        ThreadPoolExecutor executor = new MDCThreadPoolTaskExecutor(
                CPU_CORES * 2,          // 核心：8
                CPU_CORES * 4,          // 最大：16
                60L,
                TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(2000),
                new WmThreadFactory("IO-Task-Pool"),
                new RetryRejectedExecutionHandler()
        );

        log.info("Created IO-Intensive thread pool: core={}, max={}, queueCapacity={}",
                CPU_CORES * 2, CPU_CORES * 4, 2000);

        ThreadPoolMonitor monitor = new ThreadPoolMonitor(executor, "IO-Task");
        monitor.setQueueSizeAlertThreshold(80);
        monitor.setActiveThreadAlertThreshold(90);
        monitor.setBlockTimeAlertMs(1000);
        monitor.startMonitoring(300);

        return executor;
    }

    // ==================== 主编排器线程池 ====================

    /**
     * 主任务编排器线程池
     *
     * 用于：
     * - TaskChain的编排调度
     *
     * 特点：
     * - 轻量级调度，不直接执行业务任务
     * - 核心线程较少
     * - 快速分发到具体的CPU/IO线程池
     */
    @Bean("messageTaskOrchestratorExecutor")
    public ThreadPoolExecutor messageTaskOrchestratorExecutor() {
        ThreadPoolExecutor executor = new MDCThreadPoolTaskExecutor(
                3,                      // 核心：3（轻量级调度）
                6,                      // 最大：6
                60L,
                TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(1000),
                new WmThreadFactory("Orchestrator-Pool"),
                new RetryRejectedExecutionHandler()
        );

        log.info("Created Orchestrator thread pool: core={}, max={}, queueCapacity={}",
                3, 6, 1000);

        ThreadPoolMonitor monitor = new ThreadPoolMonitor(executor, "Orchestrator");
        monitor.setQueueSizeAlertThreshold(80);
        monitor.setActiveThreadAlertThreshold(90);
        monitor.setBlockTimeAlertMs(500);
        monitor.startMonitoring(300);

        return executor;
    }
}
```

#### 修改编排器代码

**MsgProcessOrchestrator.java**

```java
@Slf4j
@Component
public class MsgProcessOrchestrator {

    @Autowired
    private ValidationTask validationTask;

    @Autowired
    private MessageIdGenerationTask messageIdGenerationTask;

    @Autowired
    private PrivateMsgProcessTask privateMsgProcessTask;

    @Autowired
    private GroupMsgProcessTask groupMsgProcessTask;

    @Autowired
    @Qualifier("cpuIntensiveExecutor")  // ← 使用CPU密集型线程池
    private ExecutorService cpuExecutor;

    /**
     * 创建消息处理任务链
     */
    public TaskChain createTaskChain() {
        // 第一步：CPU密集型并行任务组（验证 + ID生成）
        TaskGroup validationAndIdGroup = TaskGroup.create("ValidationAndIdGeneration")
                .withExecutor(cpuExecutor)  // ← CPU线程池，快速执行
                .addTask(validationTask)
                .addTask(messageIdGenerationTask);

        // 第二步：条件任务 - 消息存储（IO密集型）
        ConditionalTask<Integer> messageTypeRouting = ConditionalTask.when(
                context -> {
                    MqMsgItem mqMsg = context.get("mqMsg");
                    boolean isPrivateMessage = mqMsg.getMsgData().getContactType() == 0;
                    context.put("isPrivateMessage", isPrivateMessage);
                    return isPrivateMessage;
                },
                privateMsgProcessTask,
                groupMsgProcessTask
        );

        return TaskChain.create("MsgProcessChain")
                .addTask(validationAndIdGroup)
                .addTask(messageTypeRouting)
                .onException((context, taskName, exception) -> {
                    log.error("Message process task failed: taskName={}, errorType={}, message={}",
                            taskName,
                            exception.getClass().getSimpleName(),
                            exception.getMessage(),
                            exception);
                });
    }
}
```

public class MonitorStorageOrchestrator {

**MessageMainProcessOrchestrator.java**

```java
@Slf4j
@Component
public class MessageMainProcessOrchestrator {

    @Autowired
    private MsgProcessOrchestrator msgProcessOrchestrator;

    @Autowired
    private MonitorStorageOrchestrator monitorStorageOrchestrator;

    @Autowired
    private RecallMessageOrchestrator recallMessageOrchestrator;

    @Autowired
    private IMessageService messageService;

    @Autowired
    @Qualifier("ioIntensiveExecutor")  // ← 并行组使用IO线程池
    private ExecutorService ioExecutor;

    @Value("${spring.profiles.active}")
    private String active;

    private static final String DEV_ACTIVE = "dev";

    public TaskChain createTaskChain() {
        TaskChain msgProcessChain = msgProcessOrchestrator.createTaskChain();
        TaskGroup monitorAndRecallGroup = createMonitorAndRecallGroup();

        return TaskChain.create("MessageProcessingChain")
                .addTask(msgProcessChain)
                .addTask(monitorAndRecallGroup)
                .onException((context, taskName, exception) -> {
                    String content = JSON.toJSONString(context.get("mqMsg"));
                    if (!DEV_ACTIVE.equals(active)) {
                        EagleService.sendInfo(501, "N", "MsgConsumer Process Message Fail", content);
                    }
                    messageService.processErrorMsg(content, MsgSourceType.CHAT_SVR.getValue());
                })
                .onComplete((context, taskName, result, exception) -> {
                    context.getExecutionTrace().printTreeView();
                });
    }

    private TaskGroup createMonitorAndRecallGroup() {
        ConditionalTask<?> recallTaskIfNeeded = ConditionalTask.when(
                context -> {
                    Boolean isRecallMessage = context.get("isRecallMessage");
                    return Boolean.TRUE.equals(isRecallMessage);
                },
                recallMessageOrchestrator.createTaskChain()
        );

        return TaskGroup.create("MonitorAndRecallGroup")
                .withExecutor(ioExecutor)  // ← 使用IO线程池处理并行任务
                .addTask(monitorStorageOrchestrator.createTaskGroup())
                .addTask(recallTaskIfNeeded)
                .onException((context, taskName, exception) -> {
                    log.error("Monitor and recall group failed: {}", exception.getMessage());
                });
    }
}

## 5️⃣ 系统容量瓶颈分析

### 5.1 容量计算方法论

系统的容量瓶颈取决于整个任务链路中的最小容量节点。当消息积压超过该节点的容量时，系统将无法接收新消息，导致瘫痪。

#### 计算公式

```
单个线程池容量 = 最大线程数 + 队列容量

任务组容量（并行任务） = 线程池容量 / 每条消息产生的任务数

系统总容量 = min(各阶段容量)
```

#### 任务链路容量计算

**阶段1: RabbitMQ消费层**
```
RabbitMQ预取容量 = prefetch = 1000条消息
消费线程池 = 16核心/32最大
说明：RabbitMQ会预取1000条消息，但不是瓶颈
```

**阶段2: 主编排器 (messageTaskOrchestratorExecutor)**
```
线程池容量 = 8最大线程 + 500队列 = 508个任务slot
每条消息占用 = 1个slot（主编排器为每条消息分配1个线程）
可容纳消息数 = 508条

关键特性：
- 主编排器线程会等待整个子任务链完成
- 如果子任务阻塞，主线程也被占用
- 这是整个系统的"入口"，容量较小
```

**阶段3: CPU密集型任务 (cpuIntensiveExecutor)**
```
线程池容量 = 8最大线程 + 500队列 = 508个任务slot
每条消息产生任务数 = 2个（ValidationTask + MessageIdGenerationTask）
可容纳消息数 = 508 / 2 = 254条

执行特性：
- 任务执行极快（1-10ms）
- 无IO等待，纯CPU计算
- 实际不会成为瓶颈（任务快速完成）
```

**阶段4: 消息持久化 (messagePersistenceExecutor)**
```
线程池容量 = 16最大线程 + 1500队列 = 1516个任务slot
每条消息产生任务数 = 1个（PrivateMsgProcessTask 或 GroupMsgProcessTask）
可容纳消息数 = 1516条

执行特性：
- IO密集型，执行慢（50-200ms）
- 数据库写入操作
```

**阶段5: 监控存储 (monitorStorageExecutor)**
```
线程池容量 = 16最大线程 + 3000队列 = 3016个任务slot
每条消息产生任务数 = 3个（MonitorRecordSaveTask + ElasticsearchStorageTask + HistoryChatUserStorageTask）
可容纳消息数 = 3016 / 3 ≈ 1005条

执行特性：
- IO密集型，执行慢（50-200ms）
- 大量DB和ES写入
- 最容易发生阻塞的环节
```

**阶段6: 撤回处理 (recallMessageExecutor，仅1%消息执行)**
```
线程池容量 = 8最大线程 + 2000队列 = 2008个任务slot
每条消息产生任务数 = 3个（RecallEsMessageUpdateTask + RecallMonitorMessageUpdateTask + Recall消息表更新）
可容纳消息数 = 2008 / 3 ≈ 669条撤回消息

说明：由于只有1%的消息执行撤回，不是主要瓶颈
```

#### 瓶颈识别

| 阶段 | 容量（条消息） | 是否瓶颈 | 说明 |
|------|---------------|---------|------|
| RabbitMQ预取 | 1000 | ❌ | 预取容量充足 |
| RabbitMQ消费线程 | 32 | ❌ | 消费线程充足 |
| **主编排器** | **508** | 🚨 **系统瓶颈** | 入口容量最小 |
| CPU密集型 | 254 | ⚠️ 理论瓶颈 | 实际执行快，不阻塞 |
| 消息持久化 | 1516 | ❌ | 容量充足 |
| 监控存储 | 1005 | ⚠️ 次要瓶颈 | IO阻塞会传播 |
| 撤回处理 | 669 | ❌ | 仅1%消息执行 |

#### 系统临界点

```
🚨 系统瘫痪临界点：508条消息

当积压达到508条消息时：
✓ 主编排器：8线程 + 500队列 = 508 (满载！)
✓ CPU密集型：254条消息 × 2任务 = 508任务 (满载！)
? 消息持久化：部分任务在处理中
? 监控存储：部分任务在处理中

如果此时任何一个IO任务阻塞：
→ 主编排器的508个任务全部卡住等待
→ RabbitMQ消费者无法提交新任务
→ 触发RetryRejectedExecutionHandler重试
→ 系统瘫痪，无法处理新消息
```

1. 查看线程状态分布
jstack <pid> | grep "java.lang.Thread.State" | sort | uniq -c
# 如果大量TIMED_WAITING：说明在等待IO

2. 查看线程池配置
# 核心线程数是否太少？

3. 查看任务队列
# 队列是否积压？

# 解决方案
- 增加核心线程数（CPU密集型不适用）
- 检查是否有死锁或阻塞
- 优化IO操作（如增加数据库连接池）
```

**问题3: CPU利用率过高**

```bash
# 症状
- CPU利用率 > 95%
- system CPU高（>20%）
- 上下文切换频繁

# 排查步骤
1. 查看上下文切换率
vmstat 1
# cs列 > 50000：线程数过多

2. 查看线程数
jstack <pid> | grep "java.lang.Thread.State" | wc -l
# > 200个线程：可能过多

3. 查看GC情况
jstat -gcutil <pid> 1000
# FGC频繁：可能内存泄漏

# 解决方案
- 减少最大线程数
- 增加队列容量（延迟创建线程）
- 检查内存泄漏（如ThreadLocal未清理）
```

**问题4: 响应时间长**

```bash
# 症状
- P95 > 500ms
- P99 > 1000ms
- 用户投诉延迟

# 排查步骤
1. 查看任务执行树
# 在日志中找到慢的消息，查看ExecutionTrace
context.getExecutionTrace().printTreeView();

2. 分析哪个任务慢
MessageProcessingChain [成功] - 总耗时: 850ms
├─ ValidationAndIdGeneration [成功] - 10ms
├─ MsgProcessChain [成功] - 100ms
└─ MonitorStorageGroup [成功] - 740ms  ← 这里慢！
    ├─ MonitorRecordSaveTask [成功] - 120ms
    ├─ ElasticsearchStorageTask [成功] - 620ms  ← ES写入慢！
    └─ HistoryChatUserStorageTask [成功] - 100ms

3. 针对性优化
- 如果DB慢：优化SQL、增加索引
- 如果ES慢：检查ES集群状态、批量写入
- 如果网络慢：检查网络配置

# 解决方案
- 优化慢任务
- 增加并行度（如果任务可并行）
- 异步化（如监控任务可以完全异步）
```

**4. 性能分析步骤**
