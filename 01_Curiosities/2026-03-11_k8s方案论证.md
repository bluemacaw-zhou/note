# k8s 方案论证：如何在 Mac 上实现极致能效？

## 1. 好奇心触点
作为一个拥有 32G 内存 Mac Mini 的用户，我开始思考：
- K8s 必须是笨重、费电、占满内存的吗？
- 能不能在不牺牲多节点特性的前提下，实现“按需分配”内存？
- 能不能让 K8s 镜像像本地文件一样即插即用？

## 2. 思考逻辑 (Multipass vs OrbStack)

### 2.1 传统路径：Multipass + k3s
- **好奇点**: 这是最接近生产环境的 Linux 方案。
- **思考**: 虽然稳健，但它在 macOS 下是“异物”，内存无法被宿主机智能回收。对极致能效追求者来说，4G 固定开销就是 4G 的浪费。

### 2.2 现代路径：OrbStack + k3d
- **好奇点**: 为什么 OrbStack 在 Apple Silicon 上口碑极佳？
- **发现**: 它利用了 macOS 的 Hypervisor 框架和内存气球技术。这不仅是性能问题，更是“资源哲学”问题——让 K8s 融入 macOS 资源调度。
- **镜像共享**: 这种“零流量”同步镜像的想法极具吸引力。

## 3. 深度补完：CI/CD 与本地开发闭环

### 3.1 Gitea + Actions 的本地化优势
在 OrbStack + k3d 下运行 CI/CD 的核心价值在于：
- **镜像构建的“零延迟”**: 由于 Runner 与 k3d 节点共用宿主机的容器存储，构建完的镜像几乎是“瞬间”就出现在集群的缓存中。
- **代理透明**: 容器自动继承宿主机的代理配置，彻底解决 CI 过程中拉取外网依赖包的痛点。

## 4. 架构哲学：谁在管理谁？ (Helm vs OrbStack)

### 4.1 职责重叠的真相
在本地开发环境下，Helm 和 OrbStack 似乎都在管理容器，但它们处于不同的抽象维度：
- **基础设施层 (OrbStack)**：管理虚拟机、内核、网桥、物理内存分配。它决定了这栋“楼”是否通水通电。
- **应用编排层 (Helm/K8s)**：管理 Pod 的自愈、扩缩容、服务发现、配置注入。它决定了“房间”里的功能。

### 4.2 “物业”与“精装修”的类比
- **OrbStack 是“物业”**：提供公共设施。它不关心你屋里装成什么样，只负责在你需要 512MB 内存时，通过“内存气球”技术精准地从 macOS 拨付资源，并在你不用时收回。
- **Helm 是“精装修包”**：它带着家具（Pod）、灯饰（Service）、水槽（PVC）进场。它不需要知道电梯（内核）如何运行，只需调用物业提供的标准接口。

### 4.3 为什么需要这种“重叠”？
- **自愈能力**：物业（OrbStack）不管你灯坏了没，但装修经理（K8s/Helm）发现 Pod 挂了会自动换新的。
- **复杂性粘合**：部署一个 Gitea 需要几十个组件，Helm 将其打包成一键指令，而 OrbStack 确保这些指令有底层的 Linux 动力去执行。

### 4.4 选择逻辑：AI 友好度
为了让 AI 能更好地协同，我们将 Helm 部署在宿主机（Mac）。这意味着 AI 站在“指挥官”的角度通过 API 遥控集群，而不是钻进容器内部，这极大地简化了指令路径。


## 5. 结论与假设
我假设：**OrbStack + k3d + 宿主机 Helm 是目前 Mac 用户兼顾“能效”与“AI 友好度”的最佳本地 K8s 实践方案。**
